# Private Sigstore TUF bootstrap

This opt-in tooling prepares explicit private trust distribution for strict Kyverno/Cosign verification. It does not change the installed Kyverno version, existing audit-first policies, or cluster resources. The current default profile remains Kyverno 1.18.1. The separately reviewed 1.19.2 verifier initializes TUF even when a policy includes inline `trustedRoot`, and also loads Rekor, certificate-transparency and CA trust targets.

## Offline bootstrap

`create_sigstore_tuf.py` consumes a private JSON plan with exactly `schema_version: 1`, `keys`, `expires` and `targets`.

- `keys` contains `root` (three Ed25519 PKCS8 private-key references), `targets` (three different references), `snapshot` (one) and `timestamp` (one). Every reference is an absolute `path` plus its approved SHA256. All eight public keys must differ. The helper signs with two root keys, two targets keys, one snapshot key and one timestamp key. Private files must belong to the non-root offline signing identity and deny group/other access.
- `expires` contains a UTC `YYYY-MM-DDTHH:MM:SSZ` value for each role. Expiry must remain in the future, follow timestamp â‰¤ snapshot â‰¤ targets â‰¤ root, and stay within the helper's bounded role lifetimes. No client clock or expiry check is disabled.
- `targets` contains exactly `trusted_root.json`, `rekor.pub`, `ctfe.pub` and `fulcio.crt.pem`, each with its own reviewed absolute path and hash. These are public Sigstore/log/CA trust inputs; private key material is refused. Approving the public targets is a separate operator responsibility.

Run local input inspection without signing:

```bash
python3 scripts/create_sigstore_tuf.py   --plan private/sigstore-tuf-plan.json   --output-dir private/generated/sigstore-tuf
```

On the separate non-root Linux offline authority, add `--create` to sign and write a new ignored private directory. Existing directories are never replaced. OpenSSL operations use frozen private inputs, a minimal environment, bounded time/output and no interactive password input. Keys are not generated by this helper and are not copied into the repository. Signing requires the operator to make the approved quorum of offline keys available; this does not prove independent physical custody or hardware-backed signing.

The public snapshot contains signed version-1 root/targets/snapshot/timestamp metadata, the four public targets and a status receipt. Metadata links pin both byte lengths and SHA256 values. Root and target roles require 2-of-3 valid signatures. The status receipt records file hashes and public key IDs; it explicitly leaves consumer acceptance, admission and HA verification false.

This is an initial bootstrap helper. It does not implement online refresh, root rotation, rollback recovery, key recovery/custody, an HA signing authority or expiration monitoring. Preserve recovery material independently and complete those lifecycle requirements before claiming production trust-service qualification.

## HTTPS mirror

`sigstore_tuf_mirror.py` accepts a separate private plan with exactly `schema_version: 1`, canonical IPv4 `address`, an unprivileged `port`, hash-pinned `certificate` and `private_key` references, and `files` mapping the nine public snapshot filenames to their references. TLS inputs must be outside the served public data; the TLS private key belongs only to the non-root mirror identity. No offline signing key is a mirror input.

The default command checks the snapshot locally. An explicit `--serve` starts the listener:

```bash
python3 scripts/sigstore_tuf_mirror.py --plan private/sigstore-mirror.json --serve
```

The server freezes the reviewed public bytes before listening. Only exact metadata routes and `/targets/<approved-filename>` return content. Unknown files, directory listings, traversal, encoded aliases and queries are refused. TLS handshakes and reads are bounded; plaintext serving is not offered. The client must trust an approved CA matching the mirror hostname/IP. This single-process utility is a building block; it is not an HA installation or a substitute for three admission replicas and redundant serving/storage.

## Real consumer test

The gated `test_valkey_gateway.GatewayTests.test_real_kyverno_private_tuf_signature_verification` case uses actual Harbor, Cosign, a TLS Rekor log and the checksum-pinned Kyverno 1.19.2 CLI. It creates a fresh threshold-signed private TUF snapshot and HTTPS mirror. Each CLI evaluation uses a new isolated HOME/TUF cache, explicit private CA and a repository pull-only token; the network namespace has no upstream route. No TLS, transparency, SCT, signature or expiry bypass is enabled.

The case requires a valid signed image and signed annotations to pass, and wrong annotations, tampered trust-target bytes and an insufficient root-signature threshold to refuse. Signer, mirror and reader identities are separated. Supplemental CT/CA inputs satisfy the key-based verifier's infrastructure initialization; this case does not establish running keyless Fulcio or certificate-transparency services. All raw diagnostic output and receipts stay under ignored `private/validation` paths.

Actual Kubernetes admission, three ready admission replicas on separate nodes, webhook/policy identity checks, workload rollout under Deny/Fail, service failure recovery and the full CI-to-admission-to-Argo qualification remain separate required work. A CLI verification result must not be reported as admission enforcement.

The separate [optional Kyverno installer](KYVERNO_INSTALLATION.md) preserves the three-admission/two-background/two-cleanup/two-reports profile and explicit namespace/private-CA identity. Its gated VM test exercises actual admission separately from the CLI case. Neither component test establishes full foundation or stack HA.
