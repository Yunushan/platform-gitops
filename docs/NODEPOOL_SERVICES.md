# Guarded static Nodepool launcher packages

Status: deployment artifacts and startup guards, not live worker allocation or
HA acceptance. Use the [static worker contract](NODEPOOL_STATIC.md), matching
[Zuul packages](ZUUL_SERVICES.md) and [full-stack requirements](MULTI_RUNTIME_STACKS.md).
The [ZooKeeper member packages](ZOOKEEPER.md) can provision candidate service
artifacts for the shared coordination dependency; they do not establish working
sessions or replace its PKI/ACL and live acceptance requirements.

## Render without registration

The service renderer uses the same two private plans as the static configuration
renderer, including explicit tenant worker-label restrictions:

```bash
python3 scripts/render_nodepool_services.py \
  --plan private/nodepool-static.json \
  --zuul-plan private/zuul-config.json \
  --runtime rke2 \
  --output-dir private/generated/nodepool-services-rke2
```

Other target selections are `k3s`, `k8s`, `docker` and `raw`. Output must be a new
ignored private directory. No image is pulled, workload applied, controller
started or worker registered by rendering. Real hostnames, host keys and tenant
inventories are private even though they are not passwords.

**Starting these packages is a separate write action:** the real launcher can
change ZooKeeper worker registrations and allocations. Review the worker reset
policy, live tenant restrictions, coordination services and selected release
pair before enabling it. Static host state is not automatically reimaged or
isolated by these packages.

## Startup guard

The embedded `start_nodepool.py` is a read-only local-input checker unless
`--start` is explicitly supplied. For launch, it requires:

1. A dedicated non-root Linux service identity and existing state directory.
2. A configuration file matching the exact digest generated by the renderer.
3. The three private ZooKeeper TLS input files as bounded regular files.
4. Installed `nodepool` and `nodepool-launcher` tools whose reported versions
   match the reviewed stable release exactly.
5. Successful configuration validation by that installed Nodepool CLI, followed
   by another digest check before the foreground launcher handoff.

The [Nodepool operations reference](https://zuul-ci.org/docs/nodepool/latest/operation.html)
documents its version/configuration options, foreground launcher, PID file and
SIGINT shutdown. The packages disable its status webapp and do not enable the
interactive REPL. No worker SSH private key, database password or cloud API
credential is passed to this static launcher; the executor's build-node identity
is provisioned separately.

Local certificate-file metadata is not a cryptographic or connectivity test.
Declared versions/digests do not prove provenance or Nodepool/Zuul API
compatibility. Unrecognized version output fails rather than skipping the check.
The Nodepool CLI checks in fixture tests are simulated, not real binary/schema
acceptance. Treat application logs as private; captured guard diagnostics are
not echoed, but upstream runtime logs need their own review.

The configuration hash protects the launch boundary, not every future read.
Nodepool can re-read configuration while running. Keep host configuration under
approved immutable/private deployment control; render a new bundle and perform
a reviewed rollout rather than modifying files opportunistically in place.

## Kubernetes

The renderer emits an immutable content-addressed ConfigMap, a two-replica
launcher Deployment with node anti-affinity, and a PDB. It does not create a
Service, public port, image builder, job worker, Secret or API role.

Provision the selected namespace and a private `nodepool-zookeeper` Secret with
`zk-client.pem`, `zk-client.key`, and `zk-ca.pem`. Use an appropriately restricted
client identity for the same coordination namespace and server endpoints as
Zuul. Effective ACLs, key correspondence, certificates, DNS and connectivity
must be verified independently. No Kubernetes API token is mounted.

The selected image must provide Python 3, Nodepool and its required plugins and
dependencies. Pods run as UID/GID 1000, without capabilities, with read-only root
filesystems and separate bounded ephemeral local state. The authoritative
coordination state is not backed up by those directories. Resource requests and
limits are starting constraints, not production sizing evidence.

SIGINT is requested through an in-container pre-stop hook, with a bounded wait
inside the Pod termination deadline. It targets that container's PID 1, not a
host process; the template never enables host PID sharing. Verify graceful
shutdown for the exact image/runtime. Do not copy the hook onto a host shell.
The local process/container status does not establish successful registrations
or availability of useful workers.

Two candidate replicas and a PDB are **not** proof of a safe HA allocation
design. Before accepting that topology, test the selected static driver's
cooperation against the exact Nodepool/Zuul releases: simultaneous requests,
duplicate-host prevention, release, stale sessions, launcher loss and recovery.
Do not start multiple independent inventory cohorts with conflicting definitions
against one coordination namespace.

Apply only after review using an explicit cluster context and server-side apply.
No application of these manifests was performed during structural tests.

## Docker

The Compose service has no published ports, no elevated capabilities, a fixed
guarded entrypoint and no inherited image CMD. Provision readable `private/`
TLS files and writable `state/` beneath the generated bundle for UID/GID 1000.
Bind sources must exist; automatic creation and ownership resets are disabled.

Docker shutdown uses SIGINT with a bounded grace period. A single Compose
service on one host is not HA; independent hosts, coordination and failure tests
remain an explicit integration requirement. Compose parsing is tested without
an engine, pull or running Nodepool container.

## Native Linux

Install approved Python/Nodepool tools under `/opt/nodepool/bin`, place the
generated helper modules/configuration under `/etc/nodepool`, and provision the
private TLS subdirectory separately. Create the `nodepool` service user/group.
The unit establishes its state directory, runs without capabilities, confines
filesystem writes, selects SIGINT shutdown and applies resource limits.

The renderer does not install packages, create users, enable services, modify
workers or configure network routing. For a multi-host design, validate the
same shared-coordination and duplicate-allocation properties required for the
Kubernetes candidate topology.

## Required remaining acceptance

Verify the selected release pair and real CLI schema, then TLS/ACLs and actual
allocation/release behavior. Test wrong host keys, label-escape attempts,
concurrent assignments, launcher/worker failure, job logs, stale sessions and
restoration. Static worker cleanup/reimage and cross-job credential isolation
remain open prerequisites for mutually untrusted jobs. Ephemeral provider
adapters are still required where static reuse cannot meet the trust policy.

No live Nodepool controller, allocation or reset was run by fixture tests. All
generated registration, allocation and HA acceptance flags remain false.
