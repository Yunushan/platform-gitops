# Flux controller packages and guarded deployment

Status: the opt-in deployment helper has reconciled private Git revisions and
served artifacts during source-leader loss in a disposable K3s lab.
The lab also verified application rollout and drift correction after that
loss. Upgrades, restore, and the full Gerrit and GitLab stacks still need
acceptance. See the
[multi-runtime expansion](MULTI_RUNTIME_STACKS.md).

## Runtime and release inputs

Flux controllers always run on an explicit Kubernetes management target.
RKE2, K3s and existing Kubernetes can provide that target. For Docker/native
application hosting, select the management context separately. This package
does not install a hidden cluster, run Kubernetes controllers as native daemons,
or turn a Kubernetes reconciliation into Docker/SSH application deployment.
Those application-host integrations remain required work for the full stacks.

Copy [the example plan](../examples/flux.json) into `private/flux.json` and fill
every placeholder. Choose an exact reviewed Flux 2.x release, export that release's
components, record the export SHA-256, and independently review/pin every image
digest. A toolkit release contains components with their own version numbers.
The `flux_version` field records the operator's release selection; the export
hash pins the bytes. The renderer does not attest that the declared version or
image digest came from an authentic release. Verify provenance, compatibility,
licenses and signatures through the normal artifact review process.

For example, with a separately verified Flux CLI, prepare a four-controller
export without installing it:

```bash
flux install --version=v2.6.4 --namespace=flux-system \
  --components=source-controller,kustomize-controller,helm-controller,notification-controller \
  --export > private/flux-install.yaml
```

The version above is a compatibility-test example, not a latest-release
recommendation. The [upstream install command](https://fluxcd.io/flux/cmd/flux_install/)
documents explicit release selection and export. A full upstream `install.yaml`
may also contain the image-reflector and image-automation controllers. If they
are present, declare their image pins too. Unknown or omitted controller pins
stop generation; no exported controller is silently discarded. The base must
already target the selected namespace. The generator does not guess how to
rewrite a different namespace across release RBAC and endpoint configuration.

## Controller candidates and artifact availability

Every selected controller gets two candidates, leader election, required
failure-domain anti-affinity, explicit node selection and a budget retaining one
available pod during voluntary eviction. Rollouts use zero surge and one
unavailable pod so two eligible failure domains can make progress. Candidate
replicas are not evidence of failover, fencing, capacity or HA storage.

The reviewed source-controller implementation starts its built-in artifact
listener only after winning the lease. A Service selecting healthy standby
pods would therefore route some requests to a missing listener. This is visible
in the [source-controller v1.6.2 startup path](https://github.com/fluxcd/source-controller/blob/v1.6.2/main.go#L277).
The package addresses artifact serving separately:

- All source candidates share one existing **ReadWriteMany filesystem** claim.
  Its storage must remain available across the chosen failure domains.
- The built-in leader-only listener moves to loopback port 9091.
- A digest-pinned NGINX Community sidecar serves the shared artifacts on port
  9090 in every candidate. The original artifact Service targets that sidecar.
- The sidecar mounts artifacts read-only, has no Kubernetes API token mount,
  drops capabilities and uses a read-only root filesystem. Its temporary files
  have a separate bounded volume. The manager receives its own projected API
  token/CA/namespace volume; automatic pod token mounting is disabled.
- Manager readiness checks its health endpoint. Sidecar readiness checks the
  artifact listener. Neither check proves a particular artifact can be fetched.

The NGINX image must contain a compatible Linux `nginx` executable, runnable as
UID/GID 1337. Startup uses the supplied configuration directly. Directory listing
and write methods are disabled; artifact links generated by source-controller
retain normal filesystem behavior. Only the controller should write this claim.
Review claim permissions, atomic rename behavior, capacity and garbage collection
under concurrent reads. An RWX access-mode declaration alone proves none of these.

This artifact endpoint follows the original Flux internal HTTP protocol. Keep
the reviewed Flux network policies and provide the required Cilium/network
transport encryption and isolation. This adapter does not claim inter-controller
mTLS, tenant isolation or storage confidentiality from its replica count.

## Scoped reconciliation

The plan selects a separate workload namespace, one exact Git branch/subdirectory,
a pre-existing read-credential Secret reference and a pre-existing reconciliation
service account. HTTPS URLs must have no embedded credentials; SSH URLs may name
the login but never a password. No plain HTTP or insecure TLS switch is accepted.
Provision the read credential, SSH host pins or HTTPS trust privately using the
selected Flux release's credential contract. The renderer writes no credentials.

For recovery, point `sync.url` at the authenticated HTTPS or SSH service
hosting the restored repository and set `sync.commit` to the full lowercase
SHA-1 recorded for the deployment. Keep `sync.branch` set to the branch
containing that commit. With the pin present, later branch updates wait
until you change or remove the pin in the reviewed plan and redeploy the
sync objects. Plans without a pin follow the selected branch.
[Flux GitRepository commit selection](https://fluxcd.io/flux/components/source/gitrepositories/#commit-example)

The generated GitRepository and Kustomization refer to those identities. The
Kustomization impersonates the chosen service account and does not force resource
replacement. Provision its actual Role/RoleBindings according to the selected
repository content and allowed namespaces; this helper grants no cluster-admin
role to the workload account. A reference to a service account is not proof that
its permissions are restricted. Verify denied operations as well as allowed ones.

The generated Kustomization waits for workload health. For a Deployment,
give the reconciliation account read access to ReplicaSets and Pods in the
workload namespace so Flux can assess their status. In the K3s lab, the
Deployment reached one Ready replica while Flux's health check remained
pending. Namespace-scoped `get`, `list`, and `watch` for these child
resources allowed the same reconciliation to finish. The account still
had no access to Secrets or Nodes.

`sync.prune` is explicit and defaults to false in the example. Enabling it
authorizes Flux to delete previously managed workload objects removed from Git.
The deployment helper itself never runs `kubectl delete` or apply pruning.
Before switching from Argo CD, establish exclusive ownership of the affected
workloads; do not let both reconcilers apply competing desired state.

## Generate and inspect

Pre-provision the dedicated controller namespace, eligible nodes, healthy RWX
claim, workload namespace, scoped service account and private source-read Secret.
These are inspected before any server-side change.

```bash
python3 scripts/render_flux.py \
  --plan private/flux.json --bundle private/flux-install.yaml \
  --runtime rke2 --output-dir private/rendered-flux
```

Other application runtime selections are `k3s`, `k8s`, `docker` and `raw`. The
controller destination still comes from `management_target`. Output must be a
new directory under `private/`; existing output and public/escaped locations are
refused. The bundle includes transformed components, scoped sync objects and a
deployment contract binding their exact bytes and inventory.

The render status contains `contract_sha256`. Supply that separately reviewed
hash when checking or applying the package:

```bash
python3 scripts/deploy_flux.py \
  --bundle-dir private/rendered-flux --contract-sha256 '<REVIEWED_CONTRACT_SHA256>'
```

Without a mode flag this reads only local files, contacts no cluster and changes
nothing. To contact the reviewed target, set the environment variable named by
`management_target.kubeconfig_env` to the private kubeconfig path and add one of:

- `--check-server`: verify HTTPS configuration, context/cluster binding, storage,
  required identities and ownership, then server-dry-run the component package.
  Workload sync validation is deferred until its CRDs are installed.
- `--apply`: perform those checks and the ordered deployment below.

The target is bound to the **kube-system namespace UID**, not a context label
alone. Obtain it through your already verified management connection and record
it privately. The helper does not change kubeconfig contexts, copy credentials,
permit insecure API verification or contact an implicit ambient context.

## Deployment order and retry

The explicit apply path uses server-side apply without forcing field-ownership
conflicts. It refuses existing Flux objects missing this package's ownership
label, preserving installations managed by other tools. The selected namespace
and storage are pre-provisioned prerequisites. Existing unmanaged Flux adoption
and a second installation sharing global CRDs require a separate migration plan.

1. Check the target, bound RWX claim, workload account and read-secret name.
2. Inspect component ownership and dry-run the reviewed component bytes.
3. Apply the components, wait for CRDs to be established, then wait for every
   selected controller rollout.
4. Check sync-object ownership, dry-run and apply the scoped GitRepository and
   Kustomization.
5. Wait for both Ready conditions at current generations, require the
   Kustomization's applied revision to match the captured Git artifact revision.
   Require the configured commit when pinned and re-read the source to detect
   changes during that check.

The helper retains the verified manifest bytes in memory during server checks,
so editing disk files mid-check cannot change what is submitted. API operations
and captured output are bounded. Raw API/controller details are suppressed from
public output; use private diagnostics to investigate a failure.

Failures retain partial state for inspection and idempotent retry. No automatic
rollback, deletion or ownership override is attempted. A successful result sets
only deployment and current bootstrap-readiness flags. Application drift,
rollout, reconciliation correctness, node loss, artifact availability and restore
remain separate acceptance gates; their flags stay false.

## Verification scope

Tests exercise the transformed topology, read-only sidecar/token separation,
wrong-target and storage/ownership rejection, deployment ordering, byte retention,
and stale generation/revision rejection. An optional `FLUX_TEST_EXPORT` path checks
the same transformation against a real reviewed upstream export. Flux v2.6.4's
complete six-controller installation export was parsed and transformed locally;
the image digests in that test are fixtures and were not deployed.

### Local K3s reconciliation and leader loss

A disposable K3s v1.35.0+k3s1 lab used the full Flux v2.6.4 export with all six
controllers, their Linux amd64 registry digests, and NGINX 1.28.2-alpine.
`deploy_flux.py` applied the reviewed package through the Kubernetes API.
Flux fetched a private Git repository over HTTPS using a fixture CA and read
credential. The reconciliation account could apply a ConfigMap in its
namespace and was denied access to Secrets and Nodes. The ConfigMap value
and the applied revision matched the first Git commit.

Both source candidates ran on different VM workers and mounted the same NFSv4
claim. Each NGINX endpoint returned bytes matching the source artifact's
SHA-256 digest. The test paused the VM holding the source-controller lease.
The other worker served the existing artifact before and after acquiring the
lease, published the next Git artifact, and reconciled its ConfigMap while
the original worker remained paused. The lab then resumed that VM for teardown.

An application test used the same topology to reconcile a Deployment under
restricted Pod Security. After the leader VM was paused, the surviving
controllers fetched the next commit and submitted the new pod template. The
previous pod was on the paused VM. The test confirmed the hypervisor fence
and removed that pod's API record so Flux could finish the rollout health
check. A new pod on the surviving worker became Ready and returned the
second revision's marker from inside the container.

The test changed the live ConfigMap value and scaled the Deployment to zero.
After an explicit Kustomization reconciliation request, Flux restored the
Git value and replica count and a new pod became Ready. The source and
applied revisions remained equal to the same Git commit throughout the
drift repair. The original VM remained paused until the test finished.

The NFS server ran on the surviving control VM. These observations cover
controller failover with storage available. Physical node failure,
storage-server failure, Ceph/Rook, Cilium policy enforcement, upgrades, and
full application backup and restore need separate acceptance.

### Local recovery from a standalone Git bundle

A separate network-isolated lab used the same Flux and K3s versions. It
restored a reviewed branch into a fresh bare repository from a verified
bundle, advanced the restored branch to a different commit, and removed
the original checkout before starting the recovery Git service. Flux
bootstrapped from that service using a read credential and fixture CA.
The Git artifact and Kustomization reported the pinned commit, and the
live ConfigMap contained the value from that commit. The new branch tip
carried a different value. See the [GitOps source recovery
procedure](MULTI_RUNTIME_STACKS.md#keep-a-gitops-source-copy-outside-the-platform).

### Prepare an offline controller cache

Keep a reviewed recovery plan outside the transferred cache. Set
`offline_images` to `true` and `sync.commit` to the full commit ID recorded
with the Git bundle. Set the export SHA-256, image digests, source URL and
management target in that plan. The renderer sets `imagePullPolicy: Never`
for all controllers and the artifact server when offline images are selected.
[Kubernetes image pull policy](https://kubernetes.io/docs/concepts/containers/images/#image-pull-policy)

The source cache must contain the exact exported `install.yaml`, one
uncompressed `<controller-name>.oci.tar` for each selected controller,
and `nginx-unprivileged.oci.tar` for the artifact server image. Each OCI
archive must carry the exact digest reference named in the plan as its
containerd image name. The cache helper verifies Linux amd64 images.

```bash
python3 scripts/prepare_flux_recovery.py create \
  --source "$FLUX_ARTIFACT_CACHE" --directory "$FLUX_RECOVERY_CACHE" \
  --reviewed-plan "$FLUX_RECOVERY_PLAN"

# After transfer, verify again from the reviewed checkout.
python3 scripts/prepare_flux_recovery.py verify \
  --directory "$FLUX_RECOVERY_CACHE" --reviewed-plan "$FLUX_RECOVERY_PLAN"
```

Import the verified archives on every eligible node under the digest
references in the plan. Render using `$FLUX_RECOVERY_CACHE/install.yaml`
as `--bundle`, then deploy with the normal [deployment helper](#generate-and-inspect).
Provision the scoped read credential, the recovered Git service and the
bound RWX artifact claim before applying the manifests.

A follow-up K3s lab assembled and verified this cache, then imported
all six Flux v2.6.4 controller images and the artifact server image on
both workers. Every running container used the expected digest and
`Never` pull policy. The lab had no upstream network route. Flux fetched
the Git bundle's restored repository and applied the pinned commit while
the recovery branch pointed to a newer commit. The artifact claim used
NFSv4 on the disposable control VM. Recovery of production storage and
the full RKE2 stack still require a separate drill.
